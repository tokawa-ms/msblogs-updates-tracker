#### [Copilot vs. raw API access: What are you actually paying for?](https://github.blog/ai-and-ml/github-copilot/copilot-vs-raw-api-access-what-are-you-actually-paying-for/)
- 公開日時: 2026-07-22T19:00:00.000Z
- 要約: GitHub Copilotは利用量を掲載済みのAPI料金で課金する方式になり、生のAPIアクセスとの差を、モデルそのものではなく開発ワークフローやポリシー統合を含むツール層で説明した。有料プランではコード補完とNext Edit Suggestionsは引き続き含まれ、より負荷の高いチャットやエージェント作業にAI Creditsが適用される。加えてBYOKはパブリックプレビューとして、Copilotのハーネスや統合を維持したまま、トークン請求先を選んだプロバイダー側に移せる。
- なぜ重要か: 影響を受けるのは、GitHub上のIssueからPRまでを既存ツール群で進める開発チーム、利用統制を担う組織管理者、そして独自エージェントや自動化基盤を作る開発者だ。記事は、前者にはCopilotが日常の開発面を統合して提供されること、後者にはAPIがカスタム挙動や統制を自前実装するための選択肢であること、さらに既存のプロバイダー契約を持つチームにはBYOKでワークフローを変えずに請求関係を維持できることを整理している。

**重要ポイント**
- Copilotの価値はモデル呼び出し単体ではなく、エディタ、リポジトリ、プルリクエスト、Issue、ターミナル、組織統制をまたぐ開発ツールとしての接続にある。タスク単価もトークン単価だけでなく、コンテキスト選択、ツール利用、リトライ、Issueからレビュー済みPRまでの経路に左右される。
- 課金の切り分けとして、コード補完とNext Edit Suggestionsは有料プランに含まれたままで、より計算資源を使うチャットやエージェント作業にAI Creditsが適用される。
- 組織向けプランではAI Creditsを組織内でプールでき、管理者は予算設定と利用状況の追跡をbilling dashboardで行えるため、個別APIキーや未追跡スクリプトに利用が分散しにくい。
- 生のAPIアクセスは、製品機能、社内エージェント基盤、評価ハーネス、自動化パイプラインのように、プロンプト、検索、ルーティング、リトライ、ログ、セキュリティモデル、課金まで自前で設計・運用したい場合の土台として位置付けられている。
- BYOKは現時点でパブリックプレビューで、Anthropic、AWS Bedrock、Google AI Studio、Microsoft Foundry、OpenAI、OpenAI互換、xAIなどの対応モデルをCopilot Chat、Copilot CLI、VS Codeで使える。トークン課金はプロバイダー側に移るが、購買やアーキテクチャ判断の前に最新ドキュメント確認が必要だと明記されている。

<details><summary>English summary</summary>

GitHub says Copilot now meters usage at listed API rates, clarifying that the difference from raw API access is not the model itself but the workflow, policy, and tooling layer around software development. Code completions and Next Edit Suggestions remain included in paid plans, heavier chat and agentic work uses AI Credits, and BYOK in public preview keeps Copilot’s harness and integrations while moving token billing to the chosen provider.

</details>

#### [Next chapter: Restructuring GitHub’s bug bounty program](https://github.blog/security/next-chapter-restructuring-githubs-bug-bounty-program/)
- 公開日時: 2026-07-22T16:00:00.000Z
- 要約: GitHubのバグ報奨金プログラムは、恒久的な招待制VIPプログラムを正式化し、公開プログラムの報奨金体系も再編した。VIP枠は高品質・高影響の報告者に高い報奨額と速い応答を提供し、公開枠は重大度ごとの固定額に切り替わる。あわせて公開プログラムにはHackerOneのシグナル要件が導入され、新制度は2026年7月27日以降に提出された報告から適用され、既存の未処理分は旧制度で扱われる。
- なぜ重要か: 継続的に質の高い脆弱性報告を行う研究者にとっては、VIP化によって報奨額、応答速度、GitHubのセキュリティエンジニアとの連携が強化される。一方、新規参加者やシグナル閾値未達の研究者も最大4件の提出機会は残されるが、低労力やAI生成レポートの流入を抑える前提で参加条件は引き締まる。GitHubにとっては増大するキューへの対処と、より有望な報告への集中を進めるための制度変更と位置付けられている。

**重要ポイント**
- 恒久的な招待制VIPプログラムを設け、報奨額はLow 1,000ドル、Medium 7,500ドル、High 20,000ドル、Critical 30,000ドル超とした。
- VIP参加条件は、重大1件、高2件、中4件、低7件のいずれかの実績で、提出数より成果の質を重視する。
- 公開プログラムの報奨額はレンジ制ではなく固定額に変更され、Low 250ドル、Medium 2,000ドル、High 5,000ドル、Critical 10,000ドルになる。
- 公開プログラムではHackerOneのシグナル要件を導入し、閾値未達の研究者は実績を作るまで提出数が制限されるが、初期提出は最大4件まで認める。
- 変更前に提出された報告は旧制度の報奨対象のままで、新制度での査定は2026年7月27日以降の提出分から適用される。

<details><summary>English summary</summary>

GitHub is overhauling its bug bounty program by formalizing a permanent invite-only VIP tier and restructuring public payouts. The VIP track gives higher rewards and faster responses to consistently high-impact researchers, while the public program moves to fixed payouts by severity. GitHub is also adding a HackerOne signal requirement, with the new rules applying to reports submitted on or after July 27, 2026, while earlier submissions remain under the old structure.

</details>
