#### [Azure IaaS: How to design, build, and optimize cloud infrastructure for long-term cost optimization efficiency](https://azure.microsoft.com/en-us/blog/azure-iaas-how-to-design-build-and-optimize-cloud-infrastructure-for-long-term-cost-optimization-efficiency/)
- 公開日時: 2026-06-30T16:00:00.000Z
- 要約: Azure IaaSの長期的なコスト最適化に向けて、コンピュート、ストレージ、ネットワークの各層で設計・運用時に見直すべき効率化策が整理された。具体的には、VMの適正サイズ選定と料金オプションの組み合わせ、ストレージの階層化とライフサイクル管理、ネットワークの冗長化とログ収集の最適化を継続的に行う考え方を示している。あわせて、Azure IaaS Resource Centerで関連ガイダンスや技術資料を参照できるとしている。
- なぜ重要か: AI対応、既存アプリのモダナイズ、移行、将来の拡張を進めるAzure利用組織にとって、コスト増の原因を個別製品ではなくインフラ全体の設計判断として見直せる点が重要だ。特に、運用開始前から本番後まで継続的に最適化する前提を明示しており、性能や可用性を維持しながら無駄な容量、過剰な保存、不要なログ保持を減らしたいチームに直接関係する。

**重要ポイント**
- コンピュートでは、最安値を選ぶのではなく、ワークロード要件に合わせてVMのアーキテクチャや性能を選び、Pay-As-You-Go、Azure savings plans、Azure Reservations、Azure Spot Virtual Machinesを組み合わせて実使用に沿ったコスト配分を行うべきだとしている。
- 大規模なコンピュート環境では、Azure Virtual Machine Scale Setsによる自動スケールやAzure Compute Fleetによる容量・可用性・価格性能のバランス調整を使い、過剰配置を避けながら運用負荷も下げる方針を示している。
- ストレージでは、Premium SSD v2、Ultra Disk、Azure Elastic Storage Area Network (SAN)、Azure Files、Azure NetApp Files、Azure Blob Storage tiersなどを用途別に選び、アクセス頻度に応じた自動階層化とライフサイクルポリシーで長期コストを抑えるとしている。
- ネットワークでは、ExpressRoute MetroやZone Redundant NAT Gatewayなどでレジリエンシーとスケーラビリティを高めつつ、ログは必要なデータに絞るフィルタリングや分析で保存量と調査負荷を減らす考え方を示している。
- 最適化は単発の移行や価格判断では終わらず、利用状況や新機能に合わせて継続的に見直す運用規律だと位置づけており、Azure Copilotによるリアルタイム洞察、AIベースの推奨、自動最適化にも触れている。

Azure IaaS outlined long-term cost optimization practices across compute, storage, and networking. #### [6 security settings every GitHub maintainer should enable this week](https://github.blog/security/6-security-settings-every-github-maintainer-should-enable-this-week/)
- 公開日時: 2026-07-01T15:59:29.000Z
- 要約: GitHubの「Protect Your Project」は、メンテナーが30分未満で見直せる6つの無料セキュリティ設定を一度に進められる導線として紹介されている。記事は、これらを組み合わせることで、公開リポジトリの“簡単な入口”を塞げると説明する。プロジェクトを無敵にはしないが、攻撃されにくくし、その依存先にも効果が及ぶという位置づけだ。
- なぜ重要か: 主に対象となるのは、セキュリティ専任ではないGitHubメンテナーだ。設定画面やドキュメントの複雑さで後回しにされがちな基本防御を、短時間でまとめて有効化できる点に意味がある。結果として、公開リポジトリを自動的に狙う攻撃者に対する露出を減らし、そのプロジェクトの利用者や依存先にも保護効果が及ぶ。

**重要ポイント**
- まずSECURITY.mdを追加し、続けてprivate vulnerability reportingを有効化することが推奨されている。前者で報告先と対象範囲を明示し、後者で研究者が公開前に機密のadvisoryを送れるようになる。PVRの設定はSettings → Securityのチェックボックス1つとされる。
- secret scanning with push protectionは、公開GitHubでの秘密情報漏えい増加を踏まえた対策として挙げられている。本文は2025年に2,865万件の新規シークレット漏えい、前年比34%増、AI支援コミットは基準の約2倍の漏えい率とし、ローカルでプッシュ前に鍵やトークンを止められると説明する。

- code scanningはCodeQLを使う静的解析として案内され、unsafe GitHub Actions workflowsの検出も可能とされる。オープンソースでは2019年から無料で、Security and Qualityタブからワンクリックのdefault setupが用意され、言語に合うquery packを選んで各PRで実行すると説明されている。
- default branchのbranch protectionでは、mainへの直接マージ前にPRと最低1件の承認を必須にする設定が勧められている。これにより、侵害された認証情報や誤操作への防波堤になるだけでなく、Dependabotやcode scanningの結果を実際にマージブロックへ結びつけられる。
