### Azure Blog (1)

#### [AT&T and Microsoft scale trillion-token workloads with Microsoft Foundry and AMD](https://azure.microsoft.com/en-us/blog/att-and-microsoft-scale-trillion-token-workloads-with-microsoft-foundry-and-amd/)
- 公開日時: 2026-07-23T18:30:00.000Z
- 要約: AT&amp;Tの通信特化AIモデルOTel2.0は現在利用可能とされ、Microsoft Foundry Managed Compute上でPhi-4、OSS 120B、Gemma 4を使い分ける開発体制へ拡張された。本文では、430基のAMD Instinct MI300Xを含む約530基のGPUで約1兆トークンを処理したと説明する。AT&amp;Tは、オープンモデル活用によりフロンティアモデル利用時より数千万ドル規模のコスト削減ができたと主張している。
- なぜ重要か: 通信事業者や、業界固有データでAIを作る大規模開発チームに関係する内容である。本文は、汎用モデルだけでは通信ネットワークや標準、運用の知識が不足し得る一方、Foundry Managed ComputeならモデルとGPUを選びつつ、大量トークン処理をインフラ運用負荷を抑えて進められるというAT&amp;Tの事例を示している。

**重要ポイント**
- OTel2.0開発では、Phi-4、OSS 120B、Gemma 4を用途別に使い分ける複数オープンモデル戦略を採用し、Phi-4は月7000億超トークンのデータ準備と合成データ生成に使われた。
- 基盤面では、Microsoft Foundry Managed Compute上で430基のAMD Instinct MI300Xを含む約530基のGPUを使い、モデルの配備と拡張を数日単位で進めた。
- AT&amp;Tによれば、OTel2.0向けに約1兆トークンを処理し、約4000億トークンを学習したうえ、Phi-4などのオープンモデル活用でフロンティアモデル利用時より数千万ドル規模の節約になった。
- 本文末尾ではOTel2.0モデルが利用可能になったと案内されており、OTel 1.0のダウンロードは2500万超とされる。

<details><summary>English summary</summary>

AT&amp;T says its telecom-focused OTel2.0 models are now available and were developed on Microsoft Foundry Managed Compute using Phi-4, OSS 120B, and Gemma 4. The setup used about 530 GPUs, including 430 AMD Instinct MI300X units, to process roughly 1 trillion tokens. AT&amp;T also claims the open-model approach saved tens of millions of dollars versus frontier models.

</details>

### GitHub Blog (1)

#### [The case for a cooldown: Why Dependabot now waits before issuing version updates](https://github.blog/security/supply-chain-security/the-case-for-a-cooldown-why-dependabot-now-waits-before-issuing-version-updates/)
- 公開日時: 2026-07-23T16:00:00.000Z
- 要約: Dependabotは非セキュリティのバージョン更新PRを、リリース公開直後ではなく少なくとも3日待ってから作成する既定動作に変わった。待機期間はdependabot.ymlのcooldown設定で調整でき、追加設定なしで有効になる。背景には、悪性パッケージが公開後数時間で発見・撤回される事例が相次ぎ、その初動の危険時間帯を避ける狙いがある。
- なぜ重要か: Dependabotで依存関係更新を自動化している保守担当者や開発チームは、新版公開直後の危険なバージョンがそのままPRとして届く可能性を既定で下げられる。特に公開レジストリの依存を取り込むプロジェクトでは、保守者・研究者・自動スキャナが不正版を検知して撤回する時間を確保できる一方、長期潜伏型の攻撃には別の防御策が引き続き必要だ。

**重要ポイント**
- 対象は非セキュリティ更新で、公開から最低3日待ってPRを開く。待機期間はdependabot.ymlのcooldown設定で短くも長くもでき、既定で有効化される。
- GitHubは、2026年5月までの1年間にnpmマルウェア勧告が6,500件超、1日当たり約18件あったとし、短時間で露見する悪性公開を避ける根拠としている。
- 3日という既定値は、2018年から2026年の21件の著名なサプライチェーン事案レビューで、多くの悪性版が公開後数時間で取り下げられたことと、他ツールでも3日程度の待機が採用されていることを踏まえている。
- この対策は、公開直後に広がってすぐ見つかる悪性リリースには有効だが、長期潜伏バックドア、メンテナーの破壊的行為、ビルドシステム侵害には十分ではない。そのため、lockfileによる固定、CIでのinstall script無効化、トークン権限の限定、マージ前レビューを併用する前提になっている。

<details><summary>English summary</summary>

Dependabot now defaults to waiting at least three days before opening pull requests for non-security version updates instead of reacting immediately to a new release. The delay is configurable through the cooldown setting in dependabot.yml and is enabled by default. GitHub says this is meant to avoid the risky first hours when malicious package releases are often discovered and removed.

</details>
