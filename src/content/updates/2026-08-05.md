#### [How the GitHub legal team used Copilot CLI to streamline their workflows](https://github.blog/ai-and-ml/github-copilot/how-the-github-legal-team-used-copilot-cli-to-streamline-their-workflows/)
- 公開日時: 2026-08-04T19:02:34.000Z
- 要約: GitHub Copilot CLIによって、GitHubの法務チームは契約ドラフト作成やDMCA対応向けの内部ツールを、平文ベースの指示で自作できるようになった。契約ドラフト支援ツール「terms-ai」は、指示や資料、ワークフローをリポジトリで管理し、レビューと起案の時間を約半分に削減したと述べられている。別の事例では、平文ファイルで始まった法務ワークフローが、定義済みワークフローを実行するデスクトップアプリへ発展した。
- なぜ重要か: この内容は、法務担当者やプログラムマネージャーのような非エンジニア職で、反復的な業務を抱えるチームに関係する。記事では、従来のソフトウェア開発が中心でない仕事でも、平文やMarkdownで知識や基準をワークフロー化でき、人間のレビューを保ったまま業務の一貫性を高められる可能性があると示している。

**重要ポイント**
- 契約ドラフト支援ツールterms-aiは、主要文書をリポジトリに集約し、AI向けの指示・資料・ワークフローを一元管理する構成で、内部ドラフティング用スタイルガイドも備える。過去の契約ライブラリも参照でき、機密情報は承認済みのアクセス制御環境に置かれる。
- terms-aiの利用者は、レビューとドラフト作成の時間をおおむね半減できたと述べており、条項の一貫性と平易な文体も改善したとしている。
- DMCA通知の評価から始まった別の取り組みでは、エンジニア支援なしでも、平文のワークフロー指示・ポリシー資料・報告テンプレートを中核に法務判断を組み込めた。その後、クライアント向けと弁護士向けの分析モードや外部データ連携が追加され、現在は定義済み法務ワークフローを実行するデスクトップアプリへ発展している。
- この法務向けCopilotは法的判断の置き換えではなく、読みやすいMarkdownで振る舞いを制御しながら、人間のレビューを中心に据える意思決定支援システムとして位置付けられている。

<details><summary>English summary</summary>

GitHub Copilot CLI enabled GitHub’s legal team to build internal tools for contract drafting and DMCA-related workflows using plain-language instructions. One example, the terms-ai drafting tool, organized instructions, resources, and workflows in a repository and reportedly cut review and drafting time roughly in half. Another example started with plain-language workflow files and later evolved into a desktop app for predefined legal workflows.

</details>

#### [Turn one giant AI-generated pull request to a reviewable stack](https://github.blog/engineering/turn-one-giant-ai-generated-pull-request-to-a-reviewable-stack/)
- 公開日時: 2026-08-04T16:47:18.000Z
- 要約: GitHub stacked pull requestsでは、AI生成の巨大な単一PRを、依存関係に沿った小さくレビュー可能なPRスタックへ分解する進め方が示された。例では商品検索機能をL1〜L4の4層に分け、gh stackとgh-stack skillでエージェントに各層の作成と提出を担当させる。下位層の修正後もgh stack rebaseやgh stack syncで上位層へ変更を反映し、レビューしやすさと更新の追随性を保つ。
- なぜ重要か: コーディングエージェントで大きな機能を一気に実装しがちな開発者と、その差分を読むレビュアーに特に関係する。記事の手法では、巨大PRで起きるレビュー停滞や文脈喪失を避けつつ、データ担当やUI担当など層ごとに適したレビューを割り当て、下位層の修正も上位へ手作業なしで波及できる。

**重要ポイント**
- スタックの起点となるstack baseを先に決める必要があり、CIチェックとマージルールはその基準ブランチに対して各層で評価される。
- 記事の例では商品検索を4層に分割し、L1で型付きカタログとシードデータ、L2で/api/products/search、L3でチャットのAPI接続、L4で商品引用カード付きUIを積み上げる。
- 導入時はgh extension install github/gh-stackでCLI拡張を入れ、エージェント向けにはgh skill install github/gh-stack、またはnpx skills add github/gh-stackを使ってスタック操作を学習させる。
- 下位ブランチをレビュー後に更新するとスタック全体がdivergeしうるため、Web UIのRebase stackはコミッター再設定や未署名コミットに注意が必要で、端末からgh stack rebaseとgh stack syncで追随させる方法が示されている。

<details><summary>English summary</summary>

GitHub stacked pull requests are presented as a way to split one large AI-generated PR into a dependency-ordered stack of smaller, reviewable PRs. In the shopping-assistant example, product search is broken into four layers and managed with gh stack plus the gh-stack skill. After fixes to a lower layer, gh stack rebase and gh stack sync propagate changes upward while keeping the stack reviewable.

</details>
