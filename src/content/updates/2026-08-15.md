### Azure Blog (1)

#### [The Economics of Agent Optimization: From pilots to measurable returns](https://azure.microsoft.com/en-us/blog/the-economics-of-agent-optimization-from-pilots-to-measurable-returns/)
- 公開日時: 2026-08-12T16:00:00.000Z
- 要約: Microsoft Foundryは、AIを単発の実証から継続的に費用対効果を管理する「managed investment system」として運用する枠組みを前面に打ち出した。記事は、コストはモデル選定だけでなくトークン量やエージェントのワークフロー設計でも増減すると整理し、実行時の最適化、継続的な改善、支出ガバナンスを組み合わせる考え方を示している。現時点で一部機能は提供中だが、Foundryネイティブの予算と強制適用は「available soon」、より細かな帰属表示はロードマップ上だとしている。
- なぜ重要か: この内容は、AI導入を実証から本番運用へ進め、予算審査や費用説明を求められる企業チームに直接関わる。特にMicrosoft Foundry上で構築する組織にとって、エンジニアリング、財務、プロダクトが同じ支出指標でAI利用を把握し、どこで最適化や制御をかけるべきかを整理するための指針として位置付けられている。

**重要ポイント**
- AIコストはモデル単価だけでは決まらず、システムプロンプト、会話履歴、ツール定義、取得コンテンツなどの入力トークンに加え、エージェントの再試行や複数ツール呼び出しでも膨らむ。単純な追加入力でも、ステートレスなモデルに毎回フルコンテキストを送るため、費用が時間とともに増えることがある。
- 実行時の最適化策として、FoundryはModel routerで各プロンプトをcost、quality、balancedの各モードに振り分け、キャッシュやファインチューニング、Foundry IQによる必要最小限の文脈選択を組み合わせて、過剰な高性能モデル利用や不要な入力トークンを抑える考え方を示している。
- エージェントの運用最適化では、Agent optimizerが自前の評価器でプロンプト、モデル、ツール、スキルを比較して最適構成を昇格させ、場合によってはより小さく安価なモデルでも品質を維持できるとする。さらにToolboxesで必要なツールだけを送り、procedural、user、session memoryで履歴全体の再送を減らす。
- 支出統制については、現在はAzure API ManagementのAI GatewayをFoundryの前段に置いてトークンのレート制限やクォータ、キャッシュを適用できる。一方、Foundry内蔵の予算と強制適用は今後提供予定で、エージェント単位・セッション単位までの詳細なコスト帰属表示もまだロードマップ段階としている。

<details><summary>English summary</summary>

Microsoft Foundry is being positioned as a framework for running AI as a managed investment system rather than a series of one-off pilots. The post argues that AI costs are driven not just by model choice but also by token usage and agent workflow design, and it maps Foundry’s approach across runtime optimization, ongoing workflow improvement, and spend governance. Some capabilities are available now, while native Foundry budgets and enforcement are marked as coming soon and finer-grained attribution remains on the roadmap.

</details>

### GitHub Blog (1)

#### [How to bring your software delivery workflow into GitHub with agent apps](https://github.blog/ai-and-ml/github-copilot/how-to-bring-your-software-delivery-workflow-into-github-with-agent-apps/)
- 公開日時: 2026-08-14T16:00:00.000Z
- 要約: GitHub agent appsでは、Amplitude、Endor Labs、LaunchDarkly、PagerDutyなどのサービスをGitHub内で使い、機能追加の検証から依存関係確認、段階的ロールアウト、デプロイ前のリスク評価まで進められることを、記事が4つの例で示した。記事の例では、オンボーディングの「invite your teammates」手順を見直す際に、Amplitudeでセグメント別の相関を確認し、LaunchDarklyでソロ登録者向けのフラグを設定し、PagerDutyで出荷可否を判断している。これらのagent appsはGitHub Marketplaceから利用でき、組織で有効化したうえでissue割り当て、PRコメントでの@mention、Agentsタブから使える。
- なぜ重要か: 影響を受けるのは、PRやissueを中心にGitHub上で開発を進めるチームだ。記事の主張では、既存のAmplitude、LaunchDarkly、Endor Labs、PagerDutyをそのまま使いながら、各ツールに同じ文脈を持ち回る必要を減らし、開発者とagentがGitHubワークフロー内で次のアクションを調整できるようになる。

**重要ポイント**
- Amplitudeのagentを使う例では、「invite your teammates」完了と後続リテンションの相関をGitHubから確認し、チーム利用者では相関がある一方、ソロ利用者では相関がないため、ソロ登録者だけ手順を後ろ倒しにする方向へ要件を絞り込んでいる。
- Endor LabsのagentはPRで変更された依存関係を調べ、既知の脆弱性やパッケージリスクを確認できる。記事の例では問題は見つからず、CI失敗を待たずに依存関係レビューを前倒しで実施している。
- LaunchDarklyのagentには、boolean型のfeature flag「defer-team-invite」をdefault: falseで作成し、対象を「solo-intent signups」、ロールアウトを「internal &gt; 5% &gt; 25% &gt; 100%」としてコードへ配線するよう依頼できる。対象環境で承認が必要な場合は、直接変更せず承認リクエストを作成する。
- PagerDutyのagentは、対象サービスに対するデプロイリスクを、アクティブなインシデント、直近90日間の履歴、PRで触れたファイルと過去障害箇所の関連から評価する。記事の例ではアクティブインシデントがなく、現行変更との有意な相関もないため、進めてよいと推奨している。

<details><summary>English summary</summary>

GitHub agent apps let teams use services like Amplitude, Endor Labs, LaunchDarkly, and PagerDuty directly inside GitHub to handle scoping, dependency review, rollout, and deployment risk checks. In the walkthrough, Amplitude guides a rescope for solo versus team signups, LaunchDarkly creates and wires a feature flag, and PagerDuty evaluates release risk. The apps are available through GitHub Marketplace and can be used via issues, PR comments, and the Agents tab.

</details>
