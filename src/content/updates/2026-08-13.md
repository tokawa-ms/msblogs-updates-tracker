- 要約: GitHubは2026年7月の可用性報告で、GitHub全体で性能低下を招いた8件の障害と、その後の信頼性改善の進捗を示した。基盤面ではAzure Central USへの移行が進み、7月28日にはモノリスの読み取りトラフィックが52.75%に達し、Gitトラフィックも47%まで拡大した。あわせて認証やリポジトリ、プルリクエスト関連の共有依存を減らしつつ、今四半期はCentral USで読み取り70%、書き込み30%を目標にし、2026年末までにdotcom本番トラフィックを自社データセンターから移す見通しを示している。
- なぜ重要か: GitHub Actions、プルリクエスト、API、SSH、Copilot、Git操作を日常的に使う開発者や、データ居住型Enterprise Cloud環境の顧客にとって重要な報告だ。障害の影響範囲と失敗率を具体的に示したうえで、共有依存の削減、Central USへの移行、運用監視や自動化の強化によって、単一リージョンや共有基盤の不調が広範な顧客影響に波及しにくくする方針が示されている。

**重要ポイント**
- 7月は8件の障害が発生し、特に7月8日にはデータ居住型Enterprise Cloud環境でWeb UI、REST API、GraphQL API、Actions、Packages、Copilot、Git操作まで広く影響し、最悪の環境では5xxエラー率が約96%に達した。
- Azure移行は可用性強化の中核として進み、7月28日にモノリス読み取りトラフィックの52.75%をAzure Central USで処理したほか、Gitトラフィックは47%となり、全リポジトリの29%がCentral USに第2レプリカを持つようになった。
- 共有基盤への依存削減も進み、専用ユーザーサービスがピーク時に毎秒100万件超のクエリをオフロードし、主要な認可ルックアップの80%が分離済みサービス経路へ移行した。さらに専用プルリクエストサービスは認証付き読み取りでモノリス比99.87%の同等性に到達した。
- 次の段階ではCentral USで今四半期に読み取り70%、書き込み30%を目指し、全本番サービスの稼働、書き込み移行のためのデータベースプライマリ移設、そして第2Azureリージョンによるリージョン耐性の基盤整備を進めるとしている。

<details><summary>English summary</summary>

GitHub’s July 2026 availability report details eight incidents that degraded service across GitHub and outlines the reliability work that followed. Azure Central US now handled 52.75% of monolith read traffic on July 28, Git traffic in Azure rose to 47%, and shared dependencies in authentication, repository, and pull request paths were reduced. GitHub says it is targeting 70% of read traffic and 30% of write traffic in Central US this quarter, with a path to moving dotcom production traffic out of its datacenters by the end of 2026.

#### [Write your first prompt with the GitHub Copilot app](https://github.blog/ai-and-ml/github-copilot/write-your-first-prompt-with-the-github-copilot-app/)
- 公開日時: 2026-08-12T19:00:00.000Z
- 要約: GitHub Copilot appの初心者向けガイドでは、最初のプロンプト作成は特別な書式ではなく、対象プロジェクトをリポジトリやローカルフォルダとして接続したうえで、やりたい変更を平易な英語で書き始めればよいと説明している。最初から完璧な指示は不要で、結果を見ながら詳細を足し、必要に応じてモデル選択や音声入力、エージェント切り替え、リモートセッションを使い分ける進め方が示された。
- なぜ重要か: これは、GitHub Copilot appを初めて使う開発者や、何をどう頼めばよいか迷う利用者に関係する内容だ。記事は、最初から完璧なプロンプトや全モデルの理解を求めず、既存プロジェクトを接続して小さく始め、必要に応じて入力方法や実行形態を調整できることを示しており、導入時の心理的・操作的ハードルを下げる。

**重要ポイント**
- 作業開始前に、GitHubリポジトリまたはローカルのフォルダをセッションへ接続して、Copilotが必要なコードやファイルを参照できるようにする。
- 最初のプロンプトは特別な構文不要で、たとえば「Add a most-funded sort option to the games list.」のように変更内容をそのまま書けば始められ、足りない点は後から反復的に詰められる。
- モデル選択は必須の事前設定ではなく、初めはデフォルトモデルでよく、より複雑な推論が必要なときや最初の結果が不十分なときに切り替えればよい。
- 入力はテキストに限られず、内蔵の音声入力で話した内容をプロンプト欄のテキストに変換し、送信前に確認・編集できる。
- セッション設定では別のエージェント選択やリモート制御を有効化でき、リモートセッションならWebから同じ作業を引き継げるため、別デバイスでも中断せず続けられる。

The beginner guide for the GitHub Copilot app says your first prompt does not need special syntax: connect a repository or local folder for context and describe the change you want in plain English. You can refine the request iteratively and, when needed, switch models, use voice input, change agents, or continue work through remote sessions.

</details>

#### [Your contributors are AI-first now. Is your project?](https://github.blog/open-source/maintainers/your-contributors-are-ai-first-now-is-your-project/)
- 公開日時: 2026-08-12T18:00:08.000Z
- 要約: AutoGPTは、AIエージェントが大量に作るプルリクに対応するため、従来の貢献ガイド頼みから、コード近くのAGENTS.mdやスキル、必須チェックを組み合わせる運用へ切り替えた。記事では、エージェントは目の前の文脈しか読まないため、ディレクトリ単位の指示と強いゲートを置くことで、動かないPRをほぼ出さない状態に近づけたと説明している。
- なぜ重要か: AI由来のPRが増えるオープンソースのメンテナーにとって、この記事は受け入れルールやレビュー手順をコードのそばに置き、負荷を下げながら最終判断は維持する具体策を示している点が重要だ。すべてのPRを受け入れる必要はなく、どこまで開くかの境界をメンテナー自身が調整できるという考え方が、AI前提の貢献フローに直接関わる。

**重要ポイント**
- 単なるガイドやWikiでは効果が薄く、AutoGPTはClaude向けのCLAUDE.mdから、CopilotやCodexも参照できる標準のAGENTS.mdへ寄せ、コードのあるディレクトリ横に配置する形へ進めた。
- PRテンプレートのテスト計画とスキル連携、さらにバックエンドの80%カバレッジ条件によって、エージェントが自分でアプリ起動やテスト追加まで進める流れを作り、壊れたPRをほとんど出さない運用にした。
- 人間を介在させるため、CLA未署名のPRは1週間で閉じる運用にし、レビュー指摘を解決済みにするには修正後のコミットSHAを添えた返信を必須にした。
- 運用上の注意点として、質の悪いAGENTS.mdは文脈汚染を起こしうること、GraphQL APIのレート制限、高コストな自動レビュー基盤、不要になったGitHubアプリ承認の監査が挙げられた。

<details><summary>English summary</summary>

AutoGPT moved from relying on contributor docs to a workflow that combines AGENTS.md and skills near the code with required checks to handle large volumes of AI-generated pull requests. The article says agents follow the context directly in front of them, so directory-level instructions and hard gates helped reduce broken PRs to a rare exception.

</details>
