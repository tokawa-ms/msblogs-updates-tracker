#### [The Economics of Agent Optimization: Context engineering for enterprise AI agents](https://azure.microsoft.com/en-us/blog/the-economics-of-agent-optimization-context-engineering-for-enterprise-ai-agents/)
- 公開日時: 2026-09-02T16:00:00.000Z
- 要約: Microsoft Foundryは、企業向けAIエージェントのコンテキスト設計を、Foundry IQの知識、Toolboxes、Skills、Memory、Agent optimizerを組み合わせて継続的に最適化する仕組みとして説明した。不要な文書・ツール・指示・会話履歴を毎ターン送らず、そのリクエストに必要な内容だけをコンテキストに入れることで、コストを抑えつつ品質改善を狙う。Microsoftの社内評価では、Foundry IQ knowledge basesで証拠再現率が最大54%向上し、retrieval token costsが34%減ったとする。
- なぜ重要か: 企業データや既存権限を使って複数のAIエージェントを運用する組織にとって重要なのは、知識・ツール・手順・記憶を共有基盤でまとめ、データ取得時に既存のアクセス制御を継承しながら改善を続けられる点だ。ソース更新や方針変更のたびにエージェントを作り直さずに済み、既存フレームワークとも併用しやすい。

**重要ポイント**
- Foundry IQの知識ベースは、Work IQ、Fabric IQ、Web IQ、Azure Blob Storage、SharePoint、OneLake、Azure SQLなどを横断して使え、クエリを分解して並列検索・再ランキングし、引用付きの根拠を返す。対応ソースでは呼び出し元のMicrosoft Entra ID、ACL同期、Microsoft Purview感度ラベルも尊重する。
- Microsoftの社内評価では、Foundry IQ knowledge basesはBrowseComp-Plusで証拠再現率を最大54%高め、retrieval token costsを34%下げた。記事では、その要因をagentic retrieval、semantic reranking、improved answer synthesis、より効率的なトークン利用だとしている。
- Toolboxesは、web search、code interpreter、file search、カスタムMCP servers、OpenAPI 3.0/3.1 APIs、A2A agentsを1つの管理されたMCPエンドポイントにまとめる。認証やアクセス方針、ツールのバージョンを一元管理し、tool searchによって大規模ツールライブラリの平均入力トークン消費を約97%削減したという。
- Skillsは、社内手順を中央管理された再利用可能な手続きとして提供し、新版を既定にすると、そのskillを使う全エージェントがコード変更や再デプロイなしで更新手順に従える。初期コンテキストには名称と短い説明だけを載せ、必要時だけ完全な指示を読み込む。
- Foundry Agent Serviceのprocedural memoryを有効にすると、Microsoftの評価でSTATE-BenchとTau-Benchが約5%改善した。あわせて、memoryはuser-level isolation、retention settings、time-to-live policiesで保存内容や期限を制御できる。

<details><summary>English summary</summary>

Microsoft Foundry presents context engineering for enterprise AI agents as a continuous optimization system that combines Foundry IQ knowledge, Toolboxes, Skills, Memory, and Agent optimizer. Instead of sending unnecessary documents, tools, instructions, and conversation history on every turn, it focuses on supplying only what each request needs to reduce cost while improving quality. Microsoft says internal evaluations showed up to 54% better evidence recall and 34% lower retrieval token costs with Foundry IQ knowledge bases.

</details>

#### [GitHub Copilot app for Beginners: Run several agents at once](https://github.blog/ai-and-ml/github-copilot/github-copilot-app-for-beginners-run-several-agents-at-once/)
- 公開日時: 2026-09-03T16:00:00.000Z
- 要約: GitHub Copilot appでは、同じプロジェクトで複数のエージェントセッションを並列実行でき、各セッションは独立したGit worktreeと個別のコンテキストで干渉せず進められる。記事は、セッションビューで進捗を見ながら、機能追加・アクセシビリティレビュー・テストを別々のセッションで同時に走らせる初心者向けの使い方を説明している。これにより、開発者は待ち時間や文脈の切り替え負担を減らし、レビューや判断に時間を使いやすくなる。
- なぜ重要か: 複数の開発タスクを同時に進めたい開発者に関係する内容で、GitHubは、セッションを分離して並列実行することでエージェントの進行を見張る時間や文脈切り替えの負担を減らせると説明している。特に、レビューや意思決定に時間を使いたい人ほど恩恵を受けやすい。

**重要ポイント**

- セッションビューでは複数セッションのタイトルと進捗を確認でき、作業の追跡に使える。

- 記事の例では、tailspin-toysリポジトリで funded sort の追加、アクセシビリティレビュー、テスト実行を3つのセッションに分けて同時進行している。

#### [Modern Power BI architecture choices for reporting on Azure Databricks: A performance benchmark for Power BI storage modes](https://community.fabric.microsoft.com/t5/Power-BI-Updates-Blog/Modern-Power-BI-architecture-choices-for-reporting-on-Azure/ba-p/5364286)
- 公開日時: 2026-09-03T11:30:43.000Z
- 要約: Power BIでAzure Databricks上のDeltaテーブルを扱う際の4つのストレージ方式を比較したベンチマークでは、Direct Lake on OneLakeが小～中規模や日中に繰り返し使う一般的な負荷で広く良好な性能を示した。一方、数十億行規模ではComposite Model with aggregationsが、集計テーブルで処理できるクエリで最速かつ安定したが、DirectQueryへフォールスルーする問い合わせでは優位が続かない。結果は2026年6～7月時点のPower BI内のエンドユーザー向けクエリ体験を測った比較で、万能な勝者を示すものではない。
- なぜ重要か: Azure Databricksをデータソースに使うPower BIの開発者や設計者、そしてレポート利用者に関係する内容である。記事では、ストレージモードの選択が初期段階の重要判断であり、表示が遅いレポートは利用者不満の主要因になりやすいとしたうえで、直感ではなく実測結果を基に自社データで検証する判断材料を提供している。

**重要ポイント**
- 比較対象は、同じDeltaテーブルをPower BIレポートに提供する4つの方式だった。
- 一律の最適解はなく、結果はデータ量、キャッシュ状態、フィルター条件、クエリ種別によって大きく変わる。
- Direct Lake on OneLakeは、小～中規模データや日中に繰り返し使う典型的なPower BIワークロードで競争力が高く、追加のモデリング作業なしで対話的な性能を示した。
- 数十億行ではComposite Model with aggregationsが最速かつ最も安定しており、集計テーブルで解決できるクエリでは100ms未満を維持した。ただし基盤のDirectQueryに落ちるクエリにはその優位が及ばない。
