#### [Your alt text passes automated checks. That doesn’t mean it’s any good.](https://github.blog/engineering/user-experience/your-alt-text-passes-automated-checks-that-doesnt-mean-its-any-good/)
- 公開日時: 2026-08-24T20:56:32.000Z
- 要約: GitHub Accessibility Scanner向けのalt textプラグインは、画像の代替テキストを有無だけでなく質の面でも点検できるようにし、5つの決定論的ルールを既定で実行しつつ、画像と周辺文脈を使うモデル判定をオプトインで追加した。繰り返し検出はDOM順ではなく画面上のレイアウトを見る方式に改め、誤検知を抑える設計にしている。モデル利用はGitHub Modelsのトークンが必要で既定では無効であり、偽陽性や認証背後の画像、HTMLのimg以外を十分に扱えない限界も明記された。
- なぜ重要か: アクセシビリティ検査を開発フローに組み込むチームにとって重要なのは、このプラグインが「証明できる問題」と「推測にとどまる問題」を分け、既定では低コストで予測可能な検査だけを有効にしつつ、必要なときだけモデル判定を追加できる点だ。これにより誤検知、コスト、データ送信範囲を管理しながら見直すべき画像を絞り込めるが、著者らは自動チェックを最終判断とはせず、人による確認が不可欠だと明言している。

**重要ポイント**
- 背景として、WebAIM Million 2026では上位100万ホームページの画像の16.2%でalt textが欠落し、altがある画像でも10.8%は「image」やファイル名、隣接画像の重複説明など説明不足だったとされる。
- 既定の5ルールは、欠落や空白、ファイル名、TODOのようなプレースホルダー、内容を示さない一般語、隣接画像での同一altの繰り返しといった、文字列だけで判定できる問題に限定している。対象画像の抽出にはPlaywrightのrole-based locatorを使い、alt=""の装飾画像はアクセシビリティツリーに出ないため除外する。
- 任意のalt-text-qualitycheckでは、見出し、ページタイトル、figcaption、リンクやボタン内かどうか、周辺600文字までを画像ごとに抽出し、GitHub Models経由のビジョンモデルへ渡す。ただし現状は、画像がリンク内にあることは記録しても、その画像がリンク唯一の内容かどうかまでは判定していない。
- 外部モデル利用に伴い、モデル判定ルールは既定で無効で、GitHub Modelsにアクセスできるトークンが必要になる。URLのqueryやfragmentは削除され、srcやsrcsetも伏せられる一方、一般的には画像1枚ごとに1回のモデル呼び出しが発生し、画像の多いサイトでは実行コストの大半を占めうるため、毎コミットではなく定期実行が向くとしている。
- 限界も明示されており、決定論的ルールは流暢だが誤ったalt textを見抜けず、aria-labelで補正されても検出が止まらない場合がある。モデル判定は偽陽性を出し得るうえ、認証背後の画像は再取得に失敗して未検査のまま通ることがあり、対象もHTMLのimgタグに限られる。

<details><summary>English summary</summary>

The alt text plugin for GitHub Accessibility Scanner expands checks from simple presence to quality, using five default deterministic rules plus an opt-in model-based review with image and page context. It now evaluates repeated alt text based on on-screen layout rather than DOM order, while keeping the model path off by default, requiring a GitHub Models token, and explicitly noting limits such as false positives, authenticated images, and support only for HTML img tags.

</details>

### Microsoft Fabric Blog (2)

#### [Upgrade Power BI Dataflows Gen1 to Fabric Dataflows Gen2 with the Upgrade Wizard (Preview)](https://community.fabric.microsoft.com/t5/Power-BI-Updates-Blog/Upgrade-Power-BI-Dataflows-Gen1-to-Fabric-Dataflows-Gen2-with/ba-p/5360422)
- 公開日時: 2026-08-24T15:00:00.000Z
- 要約: Dataflows Upgrade Wizard (Preview)は、Fabric容量に割り当てられた対象ワークスペースでPower BI Dataflows Gen1をFabric Dataflows Gen2 (CI/CD)へ移行しやすくした。ウィザードは既存データフローの主要プロパティを保持しつつ事前評価を行い、必要な対応や制約を把握できる。移行後はGen2項目が元のGen1を置き換え、各データフローのリフレッシュや下流依存関係の再接続などの確認作業が必要になる。
- なぜ重要か: 既存のPower BI Dataflows Gen1所有者や、それに依存するsemantic models、reports、linked dataflowsを運用するチームに関係する。Power Queryロジックを作り直さずに近代化へ進められ、同じ項目IDの維持で下流側の再マッピングを減らせる一方、下流データフローの再バインドや旧コネクタ利用先の更新は利用者側で対応する必要がある。

**重要ポイント**
- プレビュー提供の対象はFabric容量に割り当てられたワークスペースで、Power BI Dataflows Gen1項目のメニューから「Upgrade to Dataflow Gen2 (Preview)」を起動し、同じワークスペース内の他のGen1項目も追加できる。
- アップグレードではID、スケジュール、クエリ、接続を維持し、名前も必要な変更が検出されない限り保持される。完了後はGen2が元のGen1を置き換えて元に戻せないため、元のGen1を残したい場合はSave Asで別のGen2項目を作る必要がある。
- 事前評価ではReady to migrate、Needs Attention、Upgrade unavailableを表示し、Needs Attentionでは増分更新、Bring Your Own Lake storage、linked dataflows、DirectQuery利用の可能性、命名変更などを検出できる。所有者でないデータフローはそのままではアップグレードできない。
- 完了後は、各アップグレード済みデータフローのリフレッシュ、下流データフローの再保存による再バインド、残るNeeds Attention対応、旧Power BI Dataflowsコネクタ利用先のPower Platform Dataflowsコネクタへの更新が必要になる。評価では旧コネクタ利用は検出されない。
- 移行先のDataflows Gen2 (CI/CD) はGit integrationとFabric deployment workflowsを備える。Microsoft公表のベンチマークではリフレッシュ時間が1.6倍から21倍に改善したとされるが、結果はデータ、容量、コネクタ、ゲートウェイ利用、クエリ設計で変わるとしている。

<details><summary>English summary</summary>

The preview Dataflows Upgrade Wizard makes it easier for eligible Fabric-capacity workspaces to move Power BI Dataflows Gen1 to Fabric Dataflows Gen2 (CI/CD) in stages. It preserves key properties and assesses each item in advance, but after migration the Gen2 item replaces the original Gen1 and teams still need to refresh dataflows and reconnect downstream dependencies.

</details>

#### [Direct Lake Calculated Columns (Preview)](https://community.fabric.microsoft.com/t5/Power-BI-Updates-Blog/Direct-Lake-Calculated-Columns-Preview/ba-p/5357159)
- 公開日時: 2026-08-24T16:14:20.000Z
- 要約: Direct Lake on OneLake のセマンティック モデルで、計算列がプレビュー提供になった。Web モデリングと Power BI Desktop から DAX で計算列を定義でき、テーブルのストレージ モード変更や上流データの修正は不要だ。Direct Lake の計算列は User Context のみをサポートし、クエリ時に評価されて RLS/OLS を尊重する一方、リレーションシップには使えず、フィルター コンテキストも反映しない。
- なぜ重要か: Direct Lake を使う Power BI モデル作成者にとって、上流データやストレージ モードを変えずに DAX の計算列を追加できるため、Import や DirectQuery との差を埋めつつ Direct Lake のままモデリングしやすくなる点が重要だ。RLS や OLS を使う組織では、保護列に基づく派生列もユーザーのセキュリティ コンテキストで評価されるため、制限ユーザーに派生結果を見せない動作が明確に示された。

**重要ポイント**
- プレビューでは Web モデリングと Power BI Desktop で DAX による計算列を作成でき、Direct Lake のままモデル内で派生列を追加できる。
- 式コンテキストは User Context のみで、評価はユーザーがモデルをクエリするときに行われ、RLS と OLS を尊重する。ユーザー依存の式や保護列を参照しない式は通常、利用者ごとに同じ値になる。
- 制約として、計算列はクエリ時評価で実体化されないためリレーションシップや関係キーには使えず、レポートのフィルターやスライサーにも反応しない。
- 用途例として、年齢のような派生値、都市と地域の連結、多言語レポート、USERPRINCIPALNAME() を使う個別化コンテンツが挙げられている。

<details><summary>English summary</summary>

Calculated columns are now in preview for Direct Lake on OneLake semantic models. Authors can create DAX-based columns in web modeling or Power BI Desktop without changing the storage mode or upstream data. The feature supports only User Context, is evaluated at query time with RLS/OLS enforcement, and cannot be used in relationships or filter-responsive logic.

</details>
