#### [What customers value most in Microsoft Databases—from reliability to AI readiness](https://azure.microsoft.com/en-us/blog/what-customers-value-most-in-microsoft-databases-from-reliability-to-ai-readiness/)
- 公開日時: 2026-07-27T15:00:00.000Z
- 要約: Microsoft Databasesは、実運用ユーザーのフィードバックに基づく2026年のPeerSpot Customer Choice / Tech Leaderで複数の評価を獲得し、SQL Server、Azure SQL Database、Azure Database for PostgreSQL、Azure Cosmos DB全体で信頼性やAI対応力が支持された。あわせてMicrosoftは、SQL Server 2025のベクター／RAG機能や、Azure Database for PostgreSQL向けAzure HorizonDBのパブリックプレビューなど、AI時代を見据えた投資方針を示した。
- なぜ重要か: 既存のSQL Server運用者、OracleからPostgreSQLへの移行を進める組織、グローバルなAIネイティブアプリを作る開発者に関係する内容である。記事は、顧客が重視する信頼性、拡張性、運用の簡素さ、開発生産性、AI対応力に沿って、今のデータ基盤やスキルを大きく変えずにAI機能や移行支援を取り込める方向性をMicrosoftが示した点に意味がある。

**重要ポイント**
- 2026年のPeerSpotでは、SQL ServerがDBMSとRelational Database Toolsで1位、Azure SQL DatabaseがDBaaSで2位、Azure Database for PostgreSQLがOpen Source Databasesで1位、Azure Cosmos DBがManaged NoSQL／NoSQL／Vector Databasesで各1位とされた。
- SQL Server 2025では、ネイティブなベクター対応、データベース内の埋め込み生成、セマンティック検索、RAG機能により、既存のプラットフォームやスキルを変えずにAIアプリを構築しやすくする方針が示された。
- Azure SQL Databaseでは、Hyperscale、automatic tuning、elastic resource managementに加え、AI retrievalとsecure agent connectivityを打ち出し、SQLの運用負荷を減らしつつAIアプリ構築に使えると説明している。
- Azure Database for PostgreSQLでは、Azure HorizonDBのパブリックプレビューに加え、AI支援のOracle-to-PostgreSQL移行、Premium SSD v2、cascading read replicas、高性能インフラの追加が挙げられ、移行と性能強化の両面を進めるとしている。
- Azure Cosmos DBでは、顧客事例として予測困難なコンシューマーポータルにserverless、バックオフィスアプリにautoscale付きprovisioned throughputを使う構成が紹介され、最近の投資としてvector/hybrid search、semantic reranking、Global Secondary Indexesなどが列挙された。

- 要約: Dependabotは、GCToolkitの設定例で依存関係更新を日次の単発PRから、エコシステムごとの月次バッチPRへ切り替える方法を示した。groupsで"\*"をまとめ、schedule.intervalをmonthlyにし、github-actionsだけでなくmavenも追加することで、レビューやCIの負荷を減らしつつ監視対象の漏れを防ぐ。さらに、脆弱性修正のセキュリティアップデートは通常の版更新スケジュールと独立して即時発行され、version updatesには既定で3日間のクールダウンが入る。
- なぜ重要か: 活発なリポジトリの保守者、特に安定したライブラリや同一依存関係を複数ディレクトリで使うモノレポの運用者にとって重要だ。日常的なversion updatesを静かで予測可能な単位にまとめつつ、修正済み脆弱性は即時に通知されるため、レビュー待ちの更新群の中で本当に重要な修正が埋もれにくくなる。

**重要ポイント**
- groupsのmonthly-batchにpatterns: \["\*"\]を設定すると、複数の依存関係更新を1本のPRに束ねられる。
- schedule.intervalをdailyからmonthlyに変えると、更新の流れを随時発生から月1回の計画可能なバッチへ切り替えられる。weeklyも選べ、schedule.dayとschedule.timeで曜日や時刻も固定できる。
- GCToolkitの元設定はgithub-actionsだけを対象にしていたが、更新後はmavenも追加され、各エコシステムを別スケジュール・別グループで扱える。
- セキュリティアップデートは通常のversion updatesとは分離され、修正付き脆弱性が開示されるとすぐPRが作られる。ただし、この仕組みを頼るにはsecurity updatesに加えてdependency graphとDependabot alertsを有効化しておく必要がある。
- version updatesには既定で3日間のpackage cooldownがあり、新規リリース直後の更新を少し遅らせる。これはセキュリティアップデートには適用されず、cooldownオプションで日数調整や無効化もできる。

<details><summary>English summary</summary>

Dependabot’s GCToolkit example shows how to replace daily one-dependency PRs with monthly grouped batches per ecosystem. Using a wildcard group, switching the schedule to monthly, and adding Maven alongside GitHub Actions reduces review and CI noise without missing important ecosystems. Security updates still open immediately and stay separate from routine version updates, while version bumps now have a default three-day cooldown.

</details>
