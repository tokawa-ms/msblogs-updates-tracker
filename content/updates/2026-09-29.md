#### [How we found 24 Android vulnerabilities using our open source AI security agent](https://github.blog/security/how-we-found-24-android-vulnerabilities-using-our-open-source-ai-security-agent/)
- 公開日時: 2026-09-28T19:00:00.000Z
- 要約: GitHub Security Lab Taskflow Agentでは、Androidアプリ監査向けにgather\_mobile\_entry\_point\_info.yamlの追加とclassify\_application\_local.yamlの調整を行い、オープンソースのタスクフローとして自分のプロジェクトでも実行できるようにした。著者はこの仕組みでAndroidアプリの脆弱性を計24件報告しており、モバイル特有の脅威に合わせてLLMの監査手順を細かく誘導している。
- なぜ重要か: オープンソースのモバイルアプリ保守者やセキュリティ研究者にとって、自分のリポジトリに同じタスクフローを適用して監査を始めやすい点が重要だ。一方で記事は、LLMが重大度を見誤ったり現実性の低い問題も挙げたりするため、結果はモバイルに詳しい研究者がレビューする必要があると強調している。

**重要ポイント**
- 自分のプロジェクトで実行するにはGitHub Copilotライセンスが必要で、プレミアムモデルのリクエストを使う。端末では ./scripts/audit/run\_mobile.sh myorg/myrepo を実行し、中規模リポジトリでは完了まで1〜2時間かかることがある。
- Android向け最適化として、gather\_mobile\_entry\_point\_info.yamlでエントリーポイントをモバイル向けと非モバイル向けに分離し、classify\_application\_local.yamlではintentベースの脆弱性など重要クラスを各エントリーポイントとコンポーネントの文脈で確認するようにしている。
- OsmAndでは、exportedなMapActivityに任意のintent extrasを送れるため、権限のない別アプリでも設定を密かに上書きできる。これにより地図タイルの座標や経路の出発地・目的地を攻撃者サーバーへ送らせ、端末位置や移動経路の追跡につながる。
- Wikipedia Androidアプリでは、wikipedia:// のディープリンク処理とCookie判定の問題を組み合わせると、wikipedia.orgで終わる攻撃者ページをアプリ内で開かせてCookieを送信させられる。記事は、これにより複数のWikimediaプロジェクトで有効な長寿命トークンを奪う強力なアカウント乗っ取りになると説明している。

<details><summary>English summary</summary>

GitHub Security Lab Taskflow Agent added and tuned Android app auditing taskflows, including gather\_mobile\_entry\_point\_info.yaml and classify\_application\_local.yaml, so the open-source workflows can be run on your own projects. Using this approach, the author has reported 24 Android vulnerabilities and is steering the LLM’s audit process toward mobile-specific threats.

**Why it matters:** This matters to open source mobile app maintainers and security researchers because they can apply the same taskflows to their own repositories and start auditing more easily. At the same time, the article stresses that LLMs can misjudge severity and surface low-realism issues, so results still need review by a researcher with mobile security expertise.

**Key points**
- Running the taskflows on your own project requires a GitHub Copilot license and uses premium model requests. You run ./scripts/audit/run\_mobile.sh myorg/myrepo, and a medium-sized repository may take one to two hours to finish.
- For Android-specific tuning, gather\_mobile\_entry\_point\_info.yaml separates entry points into mobile and non-mobile categories, and classify\_application\_local.yaml makes the model check important classes such as intent-based vulnerabilities in the context of each entry point and component.
- In OsmAnd, an exported MapActivity accepts arbitrary intent extras, so even another app with no permissions can silently overwrite settings. That can make the app send map tile coordinates and route origin and destination data to an attacker server, enabling location and route tracking.
- In the Wikipedia Android app, combining the wikipedia:// deeplink handling flaw with the cookie-domain issue can load an attacker page ending in wikipedia.org inside the app and send cookies to it. The article says this can become a powerful account takeover with long-lived tokens valid across multiple Wikimedia projects.

#### [Highlights from Git 2.56](https://github.blog/open-source/git/highlights-from-git-2-56/)
- 公開日時: 2026-09-28T17:23:33.000Z
- 要約: Git 2.56では、競合解決後のファイルだけを安全にステージするgit add --resolvedが追加され、merge-base探索の打ち切り最適化で履歴探索性能も改善された。さらに、--path-walk repackがビットマップやdelta islandsと併用可能になり、大規模リポジトリ運用で小さいパックと高速配信を両立しやすくなった。
- なぜ重要か: この更新は、競合解決を頻繁に行う保守担当者、大規模モノレポを扱うチーム、プルリク差分やオブジェクト配信を支えるリポジトリホストに特に関係する。競合解消時の誤ステージを防ぎやすくしつつ、merge-base計算やパック生成のボトルネックを減らせるため、記事中の実例では巨大履歴やサーバー側処理の時間短縮と保存効率の改善余地が示されている。

**重要ポイント**
- git add --resolvedが新設され、インデックス上で未解決だったパスだけを対象に競合解決済みとしてステージできる。競合マーカーが残っている通常ファイルがあれば何もステージせず、競合と無関係な変更は拾わない。
- merge-base探索は、片側だけに色付けされたキューが尽きた時点で打ち切れるようになり、長い履歴の無駄な探索を削減する。記事の例では、あるモノレポで0.68秒から0.01秒、別の評価では約70倍や平均約20倍の改善、Linuxカーネルの例でも0.29秒から0.01秒への短縮が示された。
- path-walk repackは、到達可能性ビットマップとdelta islandsの両方に対応し、サーバー運用で採用しやすくなった。記事のベンチマークではFluent UIで通常の558.5 MBに対し--path-walkでは164.4 MB、約71%小さいパックになったが、この方式はまだデフォルトでは有効化されない。
- 部分クローンでは、git repack -a --filter=blob:limit=1m --drop-filteredにより、後で再取得できる大きなblobを手動でローカルから削除できるようになった。これは自動キャッシュ上限ではなく、blob:limitフィルターのみ対応で、promisor remoteが必須であり、現在のインデックスが参照するオブジェクトなど安全でないケースは拒否される。

<details><summary>English summary</summary>

Git 2.56 adds git add --resolved to safely stage only files whose conflicts have been resolved, and it improves history traversal by stopping merge-base searches earlier when possible. It also makes --path-walk repacks compatible with bitmaps and delta islands, making it easier for large repository operators to combine smaller packfiles with fast serving.

**Why it matters:** This update especially affects maintainers who frequently resolve conflicts, teams working on large monorepos, and repository hosts that power pull request diffs and object serving. By reducing accidental staging during conflict resolution and cutting bottlenecks in merge-base computation and pack generation, the examples in the article show potential gains in processing time and storage efficiency for large histories and server-side workloads.

**Key points**
- A new git add --resolved mode stages only paths that were unmerged in the index. If any selected regular file still contains conflict markers, Git stages nothing, and unrelated local changes are not included.
- Merge-base search can now stop once one side’s exclusively painted queue is exhausted, reducing wasted history traversal. The article cites drops from 0.68s to 0.01s in one monorepo, around 70x and 20x gains in other evaluations, and 0.29s to 0.01s in a Linux kernel example.
- Path-walk repack now works with reachability bitmaps and delta islands, making it more practical for server use. In the article’s Fluent UI benchmark, a normal repack was 558.5 MB versus 164.4 MB with --path-walk, about 71% smaller, though the mode is still not enabled by default.
- For partial clones, git repack -a --filter=blob:limit=1m --drop-filtered can now manually remove large blobs that can be fetched again later. This is not an automatic cache limit, currently supports only blob:limit filters, requires a promisor remote, and refuses unsafe cases such as dropping objects referenced by the current index.

</details>
