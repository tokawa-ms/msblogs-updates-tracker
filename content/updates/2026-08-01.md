### GitHub Blog (1)

#### [Don’t stop early: Case-folding source code at memory speed](https://github.blog/engineering/architecture-optimization/dont-stop-early-case-folding-source-code-at-memory-speed/)
- 公開日時: 2026-07-31T16:00:00.000Z
- 要約: GitHubが公開したRustクレートcasefoldは、ソースコード向けのcase foldingを、非ASCIIで止まらずバッファ全体を分岐なしで走査するASCII経路と、バイト空間のUnicode処理で高速化した。記事では単一コアで45 GiB/s超、ほぼメモリ帯域並みの速度に達すると説明している。Unicode側はバイト空間の演算でUTF-8のデコードと再エンコードを省く設計だ。
- なぜ重要か: 大規模なコード検索や、検索エンジン・正規表現・大文字小文字を区別しない識別子照合を実装する開発者に関係する。GitHubによれば、Blackbirdでは1億8000万超のリポジトリと480TB超のコードの全バイトをcase-foldしてから索引を構築しており、この方式はその共通処理をメモリ帯域級まで高速化しつつ、ripgrepなどと同じ制約に合わせてツール間の整合性も保つ。

**重要ポイント**
- ASCII高速経路では、非ASCIIで早期終了するよりもバッファ全体を分岐なしで走査する方が速く、breakを外すことでベクトル化が進み、純ASCIIで3.1 GiB/sから45 GiB/s超まで伸びた。
- このクレートはUnicodeのsimple foldのみ実装し、ß→ssのような複数文字へのfull foldやトルコ語向けのTurkic foldは含めない。lowercasingの代用ではなく、比較用の文脈非依存・ロケール非依存なfoldingとして位置付けている。
- メモリアロケーションは必要時まで避け、ASCIIだけなら入力バッファをそのまま返し、CJKや記号など折り畳みが起きないマルチバイト文字列もコピーしない。長さが増える例外に備える追加バッファは、入力の1.5倍+4バイトで一度だけ確保する。
- Unicode側の表現は64コードポイント単位のページビットマップと圧縮ランで構成され、テーブル全体は1776バイトに収まる。折り畳み時はコードポイントにデコードせず、little-endianのバイト加算でUTF-8列を直接変換する。

<details><summary>English summary</summary>

GitHub’s Rust crate casefold speeds source-code case folding with a branch-free ASCII path that does not stop at non-ASCII bytes and a byte-space Unicode path. The article says it exceeds 45 GiB/s on a single core, essentially reaching memory bandwidth. On Unicode input it avoids UTF-8 decode and re-encode by doing the fold in byte space.

</details>
