#### [Highlights from Git 2.55](https://github.blog/open-source/git/highlights-from-git-2-55/)
- 公開日時: 2026-06-29T17:25:25.000Z
- 要約: Git 2.55は、git repackでincremental multi-pack indexチェーンを直接書けるようにし、継続的に新規オブジェクトが増えるリポジトリでもパックメタデータを段階的に保守しやすくした。あわせて実験的なgit history fixupが追加され、ステージ済み変更を過去のコミットへ取り込んで後続コミットを積み直せる。さらにLinux向けの組み込みfsmonitor対応も加わり、大規模開発や日常運用の使い勝手を広げている。
- なぜ重要か: 新規オブジェクトが継続的に増える大規模リポジトリの保守担当者には、MIDX更新を毎回全体書き換えせず進められる点が効く。レビュー前にコミット列を整えたい開発者や、Linuxでgit statusの待ち時間を減らしたい利用者にも恩恵があり、ただし巨大リポジトリではfsmonitorのwatch数上限を調整する必要がある場合がある。

**重要ポイント**
- git repackは--write-midx=incrementalでincremental MIDXチェーンを書けるようになり、--geometric=2 -dとの併用時はrepack.midxNewLayerThresholdとrepack.midxSplitFactorに基づいて新しいtipレイヤー作成後に隣接レイヤーを圧縮する。
- 実験的なgit history fixupが追加され、indexにステージした変更を過去コミットへ適用できる。既定では対象コミットのメッセージと作者情報を保ち、衝突が起きる場合は途中状態を残さず中止し、bare repositoryでは使えない。
- 設定ベースのhooksは並列実行に対応し、hook.&lt;name&gt;.parallel = trueを付けた独立hookを同時に走らせられる。並列数はhook.jobs、hook.&lt;event&gt;.jobs、またはgit hook run -jで制御し、indexやworking treeを共有状態として扱うhookは引き続き直列実行になる。
- 組み込みfsmonitorはLinux対応となり、実装にはinotifyを使う。特権昇格は不要だがディレクトリごとにwatchが必要なため、非常に大きいリポジトリではfs.inotify.max\_user\_watchesの引き上げが必要な場合があり、ネットワークマウントされたリポジトリは引き続きopt-inだ。
- 到達可能性ビットマップ生成は不要なtree再帰回避、既存bitmaps再利用、object位置キャッシュなどで高速化され、大規模リポジトリのベンチマークでは約612秒から294秒へ短縮された。pseudo-mergesでもgit rev-list --objects --use-bitmap-indexの走査が約20倍高速化したベンチマークが示されている。

<details><summary>English summary</summary>

Git 2.55 lets git repack write incremental MIDX chains directly, making pack metadata maintenance more incremental for repositories that keep receiving new objects. It also adds the experimental git history fixup command to fold staged changes into earlier commits and replay later commits. Built-in fsmonitor support for Linux further expands day-to-day usability.

</details>

#### [Inside the Advisory Database and what happens when vulnerability volume breaks records](https://github.blog/security/supply-chain-security/inside-the-advisory-database-and-what-happens-when-vulnerability-volume-breaks-records/)
- 公開日時: 2026-06-29T16:10:20.000Z
- 要約: GitHub Advisory Databaseでは脆弱性流入が急増し、2026年5月に1,560件のレビュー済みアドバイザリを公開したものの処理が追いつかず、新規公開までの時間が1週間前後から複数週へ延びている。一方でレビュー済みデータは引き続き人手で検証され、既存アラートやデータ整合性は維持されている。GitHubはキュレーション基盤の増強、AI支援調査、上流データ連携の改善を進め、報告者には完全な脆弱性データと公開意図のあるCVE申請を求めている。
- なぜ重要か: 影響を受けるのはDependabot利用者やAPI/フィード利用者、メンテナー、研究者で、レビュー遅延は新規アラートや公開反映のタイミングを遅らせうる一方、レビュー済みデータ自体の正確性は維持される。そのため下流の利用者は信頼性を保ったまま利用を続けられるが、速度改善は報告者が完全なデータを出し、メンテナーや研究者が緊密に調整するかに左右される。

**重要ポイント**
- 2026年3〜5月は毎月6,000件超の判断を継続し、プライベート脆弱性報告は週約550件から5月の大半で週3,000件超、リポジトリアドバイザリは週約650件から週5,000件超、GitHub CNAのCVE申請は5月だけで約4,000件に達した。
- ボトルネックは品質低下ではなくスループットで、レビュー済みアドバイザリの精度やデータ基盤は維持され、CVE採番率も急増期間を通じて91〜94%だった。
- 処理遅延の背景には、曖昧なパッケージ名の特定、実際のリリース履歴に合う影響バージョン範囲の再構成、複数エコシステム横断の検証、上流データの矛盾解消といった調査負荷の高い案件増加がある。
- Dependabotの既存アラートは影響を受けず、APIやフィード利用者もレビュー済みデータの正確性は維持されるが、新規アドバイザリの反映は遅れる可能性がある。
- GitHubはキュレーション基盤の増強、AI支援調査、上流CVE情報処理の自動化を進める一方、コミュニティには完全な脆弱性データ提出と、公開意図のある場合に限ったCVE申請を求めている。

<details><summary>English summary</summary>

The GitHub Advisory Database is dealing with a sharp surge in vulnerability intake; although it published 1,560 reviewed advisories in May 2026, review times for new entries have stretched from about a week to multiple weeks. Reviewed data quality, data integrity, and existing alerts remain intact. GitHub is expanding curation capacity, AI-assisted research, and upstream data improvements while asking reporters to submit complete data and request CVEs only when they intend to publish.

</details>
