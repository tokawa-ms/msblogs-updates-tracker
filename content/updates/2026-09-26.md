#### [Ship agents faster with expanded model choice, voice agents, and continuous optimization](https://azure.microsoft.com/en-us/blog/ship-agents-faster-with-expanded-model-choice-voice-agents-and-continuous-optimization/)
- 公開日時: 2026-09-24T18:00:00.000Z
- 要約: Microsoft Foundryは、OpenAIのGPT-6ファミリー（GPT-6 Sol、GPT-6 Luna）とAnthropicのClaude Opus 5.5を追加し、エージェント向けのモデル選択肢を広げた。Foundry Agent Serviceでは、音声エージェントと長時間実行の回復性をいずれもパブリックプレビューとして投入し、同じ基盤・API・SDKで構築・運用できるようにした。さらに、本番トレースを使って品質・遅延・コストを継続改善する機能群も拡充した。
- なぜ重要か: 複数ベンダーのモデルを比べつつ企業向けエージェントを本番運用したい開発者や運用チームにとって重要だ。Microsoftは、音声、長時間ジョブ、ツール接続、評価・最適化、統制を同じFoundry基盤にまとめることで、ばらばらの開発ツールやゲートウェイ、スケジューラを個別に組み合わせる負担を減らし、本番トレースを使って品質・遅延・コストを継続的に調整できるとしている。

**重要ポイント**
- Microsoft Foundryで、OpenAIのGPT-6ファミリー（GPT-6 Sol、GPT-6 Luna）とAnthropicのClaude Opus 5.5が利用可能になり、複数プロバイダーのモデルを自社データやワークロードで比較しやすくした。
- Foundry Agent Serviceの音声エージェントはパブリックプレビューで、prompt agentとhosted agentの両方をサポートする。80超の言語と140超のロケールに対応し、Web、Microsoft Teams、Teams Phone、Twilioベースの音声チャネルへ展開できる。
- 長時間実行の回復性もFoundry Agent Serviceでパブリックプレビューとなり、接続が切れた後もhosted agentの処理を継続し、ホスト停止時の復旧を支援する。Microsoft Agent Frameworkは耐久チェックポイントからの再開を補完する。
- ツール周りでは、Toolboxesがhosted agentで既にGA、prompt agent向けにはパブリックプレビューに拡大し、Tool searchはGAとなった。公開ベンチマークを使った社内評価では、50ツールのToolboxで入力トークン消費を60％超、1,000ツールで97％超削減したという。
- 運用改善ではInsights in Foundryがパブリックプレビューで、本番トレースから問題や原因を洗い出す。Agent optimizerは今月後半のGA予定で、指示・ツール・スキル・モデル選択の変更を検証できる。ガバナンス面ではEntra/Agent 365由来の操作を実行時に反映し、AI Gateway tierとの連携は10月にプレビュー予定とされた。

<details><summary>English summary</summary>

Microsoft Foundry expanded model choice for agents by adding OpenAI's GPT-6 family, including GPT-6 Sol and GPT-6 Luna, and Anthropic's Claude Opus 5.5. In Foundry Agent Service, it also introduced voice agents and long-running resilience in public preview so teams can build and operate them on the same platform, API, and SDK. It further expanded capabilities for continuously improving quality, latency, and cost using production traces.

**Why it matters:** This matters to developers and operations teams that want to run enterprise agents in production while comparing models from multiple vendors. Microsoft is positioning Foundry as a single foundation for voice, long-running jobs, tool connectivity, evaluation and optimization, and governance, reducing the need to stitch together separate developer tools, gateways, and schedulers while enabling ongoing tuning of quality, latency, and cost from production traces.

**Key points**
- Microsoft Foundry now offers OpenAI's GPT-6 family, including GPT-6 Sol and GPT-6 Luna, and Anthropic's Claude Opus 5.5, making it easier to compare models from multiple providers against a team's own data and workloads.
- Voice agents in Foundry Agent Service are in public preview and support both prompt agents and hosted agents. They cover more than 80 languages and 140 locales and can be deployed to web channels, Microsoft Teams, Teams Phone, and Twilio-based voice channels.
- Long-running resilience is also in public preview for Foundry Agent Service, allowing hosted agents to continue work after a request disconnects and recover from hosting interruptions. Microsoft Agent Framework complements this with resume-from-checkpoint support.
- For tools, Toolboxes are already generally available for hosted agents and are expanding to prompt agents in public preview, while Tool search is now generally available. In Microsoft's internal evaluation using a public benchmark, it reduced input token usage by more than 60% for a 50-tool toolbox and by over 97% for a 1,000-tool toolbox.
- For operations, Insights in Foundry is in public preview and analyzes production traces to identify issues and likely causes. Agent optimizer is planned for general availability later this month to test changes across instructions, tools, skills, and model choice. On governance, Foundry now enforces operations originating in Entra and Agent 365 at runtime, and AI Gateway tier integration is planned for preview in October.

</details>

#### [GitHub Copilot app for Beginners: How to build custom workflows with canvases](https://github.blog/ai-and-ml/github-copilot/github-copilot-app-for-beginners-how-to-build-custom-workflows-with-canvases/)

- 要約: GitHub Copilot appのcanvasesでは、/create-canvasに平易な説明を書くと、作業フローに合わせた共有UIをエージェントが生成できる。キャンバスは双方向で、ボタンやカード、フィルターなどを通じて利用者とエージェントの双方が同じ状態を更新しながら作業できる。作成後は拡張機能として保存され、チームで共有するプロジェクト用にも個人用にも再利用できる。
- なぜ重要か: 固定的な画面に業務を合わせるのではなく、自分やチームの進め方に合わせたUIを必要とする開発者に影響が大きい。カンバン、issue triage、リリースチェックリスト、フォーム、スプレッドシートのような作業面をエージェントと共有し、コマンド送信を待つ形ではなく同時に更新しながら進められる点が重要だ。

**重要ポイント**
- キャンバス作成時は、対応させたいワークフロー、画面上で自分ができる操作、エージェントにさせたい操作の3点をプロンプトに含めるよう案内している。
- 最初に生成されたUIは出発点であり、列やフィルターの追加、未処理のプルリクエストの取り込み、その日のチェックリスト化など、説明に応じて継続的に作り替えられる。
- 共有状態は即時に反映され、利用者がボタン操作やカード移動をするとエージェント側にも別の送信や同期なしで見え、逆にエージェントに同じ機能でカード移動や項目追加をさせることもできる。
- ゼロから作らなくても、Awesome Copilotで公開されているrelease notes、kanban、issue triageなどの既成キャンバス拡張を導入し、自分のワークフロー向けに調整できる。

<details><summary>English summary</summary>

In GitHub Copilot app, canvases let you describe a workflow in plain English with /create-canvas and have the agent generate a shared UI around that work. The canvas is bidirectional, so both the user and the agent can update the same state through buttons, cards, filters, and other controls. Once created, it is saved as an extension that can be reused either for a shared project or as a personal tool.

**Why it matters:** This matters for developers who need a UI tailored to their own or their team’s workflow instead of adapting to fixed screens. It makes shared work surfaces such as kanban boards, issue triage boards, release checklists, forms, and spreadsheets collaborative with the agent, so work can progress through simultaneous updates rather than by sending a command and waiting.

**Key points**
- When creating a canvas, the prompt should cover three things: the workflow to support, what you should be able to do in the interface, and what the agent should be able to do.
- The first generated UI is only a starting point and can be refined continuously, including adding columns or filters, pulling in open pull requests, or turning it into a daily checklist.
- The shared state updates immediately: when a user clicks buttons or moves cards, the agent sees it without a separate send or sync step, and the agent can use the same built-in actions to add items or move cards.
- You do not have to start from scratch: ready-made canvas extensions for release notes, kanban, issue triage, and more are available through Awesome Copilot and can be customized for your workflow.

</details>

GitHub.com gradually migrated its UI styling foundation from CSS-in-JS to CSS Modules and was running on 100% CSS Modules by June 2026. Primer finished migrating all components by December 2024, using feature flags and existing visual regression tests to preserve compatibility during rollout. The article says the Primer migration cut server-side rendering time by 55% and component initialization time by 25%, while reducing sx usage in GitHub itself delivered 1% to 22% SSR gains on some pages.

**Why it matters:** This matters to GitHub users because it affects page rendering and component initialization speed, and to GitHub frontend engineers because it provides an operating model for rolling out a large styling-platform replacement gradually in production. In the article’s account, the important point is that GitHub removed those dependencies while keeping seven themes and high-contrast support and deploying the change across dotcom without breaking it.

**Key points**
- The Primer team chose CSS Modules because it could localize class names by default and remove client- and server-side runtime behavior. Styles were moved into CSS files next to JavaScript source and shipped as stylesheets included with page HTML.
- Primer’s migration was rolled out component by component with feature flags switching between old and new styles, while existing visual regression tests verified identical output. All Primer components had migrated by December 2024, and the reported improvements were 55% less SSR time and 25% less component initialization time.
- In GitHub’s main codebase, reducing the styled-components-based sx prop became the next major effort. It started in April 2025 with about 7,760 sx props to migrate; eight engineers migrated 6,419 over six months and saw 1% to 22% SSR gains on some pages, and the remaining 895 were reduced to 0 in three weeks in April 2026 by two engineers using Copilot coding agents.
- The final blocker to full removal was theming, because GitHub supported seven themes plus high-contrast variants through styled-components. After migrating the JavaScript theme usage and utilities as well, GitHub says it removed sx, styled-components, and styled-system from dotcom.
