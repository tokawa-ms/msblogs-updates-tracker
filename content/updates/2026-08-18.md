### GitHub Blog (1)

#### [How canvases make agentic workflows visible, steerable, and cost-efficient](https://github.blog/ai-and-ml/github-copilot/how-canvases-make-agentic-workflows-visible-steerable-and-cost-efficient/)
- 公開日時: 2026-08-17T16:00:00.000Z
- 要約: GitHub Copilot appのcanvasesを使ったJava Modernization StudioとSite Studioがawesome-copilotで利用可能になり、エージェント作業をチャットの長い履歴ではなく、永続的な共有面で可視化・承認しやすくしたという実践報告だ。記事では、ワークフロー状態の明確化、重要判断の可視化、進捗やドラフトの即時保存、人間の明示的な承認ポイントが共通設計として挙げられている。作成にはSite Studioで約2,000、Java modernization canvasで約3,000 AI creditsを要したが、反復的な作業では再プロンプトや手戻りを減らせると著者は説明している。
- なぜ重要か: GitHub Copilotのエージェントを使う開発者やチーム、特に段階が多く繰り返し発生する作業を扱う人に関係する内容だ。canvasesによって、何が実行され、何が変わり、どこで人間の判断が必要かを共有面で追跡しやすくなり、再説明や文脈の再構築にかかる負担を減らせるという点が重要である。これは製品発表というより、エージェント運用を見える化して統制しやすくする実践知の共有といえる。

**重要ポイント**
- チャットは意図出しには向く一方、実作業が始まると計画や検証、承認の履歴が埋もれやすく、canvasesは状態を明示的かつ永続的に保つ場として位置付けられている。
- Java Modernization Studioでは、評価、計画、移行タスク、検証ゲート、出荷準備といった段階を明示し、複数関係者が進行状況や判断内容を監査しやすくする設計が示された。
- Site Studioでは、個人サイト向けコンテンツ制作の進捗管理にcanvasesを使い、セクション状態の可視化、ドラフト値の永続化、明示的なレビュー地点により、反復編集での文脈散逸を抑えるとしている。
- 著者は共通パターンとして、状態定義、重要な意思決定の可視化、進捗とドラフトの即時保存、人間の承認ポイントの明示を挙げている。
- 導入コストとしてSite Studioは約2,000 AI credits、modernization canvasは約3,000 AI creditsがかかり、作成した2つのcanvasはawesome-copilotで公開されている。

<details><summary>English summary</summary>

Java Modernization Studio and Site Studio built with GitHub Copilot app canvases are now available in awesome-copilot, presenting a practical way to make agent work visible and approvable on a durable shared surface instead of in chat scrollback. The article highlights clear workflow states, surfaced decisions, persistent progress and drafts, and explicit human approval points as the core pattern. The author says the canvases cost about 2,000 and 3,000 AI credits to build, but can reduce repeated prompting and rework in recurring workflows.

</details>

### Microsoft Fabric Blog (1)

#### [Using Custom SQL Pools to balance performance and cost in Fabric Data Warehouse](https://community.fabric.microsoft.com/t5/Power-BI-Updates-Blog/Using-Custom-SQL-Pools-to-balance-performance-and-cost-in-Fabric/ba-p/5359735)
- 公開日時: 2026-08-17T22:24:40.000Z
- 要約: Custom SQL Poolsは、ワークロードごとのリソース割り当てを細かく制御できる機能で、現在はプレビュー段階にあり、近く一般提供になる予定です。割り当て課金モデルでは、ワークロードの拡張を抑えて完了時間と引き換えに課金対象のvNode使用量を下げられる場合があります。一方で、これは支出上限や月額上限を設定する機能ではなく、各ワークロードが使える倉庫リソースの上限比率を決めるためのガバナンス機能です。
- なぜ重要か: 長時間実行を許容できるETL、夜間ロード、保守処理、非対話型ジョブ、あるいは業務時間中のレポート処理が他ワークロードと競合する組織にとって影響が大きい内容です。レイテンシ重視でない処理では、Custom SQL Poolsで割り当てを抑えることで、より予測可能なリソース消費に寄せやすくなりますが、遅延に敏感なワークロードには同じトレードオフが適さないことも明示されています。

**重要ポイント**
- Custom SQL Poolsは、ワークロード分離とガバナンスを主目的としつつ、割り当て課金モデルでは消費量にも間接的な影響を与える機能として位置付けられている。
- 記事の例では、制限なしだと10 vNodes・10秒・約600 billed vNode-secondsだったバースト型クエリが、倉庫リソースの50%に制限したCustom SQL Poolでは5 vNodes・20秒・約300 billed vNode-secondsとなり、完了は遅くなる一方で課金対象リソースは減った。
- 消費量の最小化を狙う場合はOptimize for Readsを無効化する案が示されており、キャッシュ有効時はアクティビティ後も最低5分間リソースが割り当てられ続けるため、計算消費が増える可能性がある。
- この機能は支出制限や月額予算上限の仕組みではなく、各ワークロードがアクセスできる倉庫リソースの最大シェアを定義するガードレールとして使う。

<details><summary>English summary</summary>

Custom SQL Pools let customers control resource allocation by workload and are currently in preview, with general availability coming soon. In an allocation-based billing model, they can reduce billed vNode usage by limiting workload scaling and accepting longer runtimes. They are not a spending cap, but a governance mechanism that sets the maximum share of warehouse resources each workload can use.

</details>
